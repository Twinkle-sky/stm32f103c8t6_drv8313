# STM32 工程编译流程详解

## 0. 总体流水线

```
点击编译按钮 (VS Code / CubeMX IDE)
        │
        ▼
cmake --build build/Debug          ← CMake 只当"调度员"，自己不编译
        │
        ▼
调用 ninja (w64devkit 自带的 ninja.exe)
        │  读取 build/Debug/build.ninja（编译说明书）
        ▼
按依赖图逐个调用:
  arm-none-eabi-gcc -c xxx.c -o xxx.c.obj    ← 编译
  arm-none-eabi-ar qc libxxx.a *.obj         ← 打静态库
  arm-none-eabi-gcc *.obj -o firmware.elf    ← 最终链接
```

关键点：**CMake 不编译代码，本工程没有 Makefile，clang 也不参与编译**。
真正干活的是 Ninja 和 `arm-none-eabi-gcc`。

## 1. 配置阶段（CMake 的工作）

点击编译按钮后，IDE 实际执行的命令大致是：

```
cmake --build build/Debug --preset Debug
```

如果 `build/Debug` 还不存在（或 CMakeLists.txt 有改动），会先触发**配置阶段**，
由 `CMakePresets.json` 指定一切：

| 配置项 | 本工程的值 | 出处 |
|---|---|---|
| 生成器 | **Ninja**（不是 Makefile！） | `CMakePresets.json` 第 7 行 |
| 构建目录 | `build/Debug/` | 第 8 行 `binaryDir` |
| 工具链文件 | `firmware/cmake/gcc-arm-none-eabi.cmake` | 第 9 行 |
| 编译器 | `arm-none-eabi-gcc / g++`（Arm GNU Toolchain 13.3 rel1） | 工具链文件第 11-13 行 |
| CPU 标志 | `-mcpu=cortex-m7 -mfpu=fpv5-d16 -mfloat-abi=hard` | 工具链文件第 25 行 |

配置阶段 CMake 依次做了：

1. **读工具链文件**：知道目标是裸机 ARM（`CMAKE_SYSTEM_NAME=Generic`，即无操作系统
   的交叉编译），编译器前缀是 `arm-none-eabi-`，可执行文件后缀强制为 `.elf`。
2. **解析 CMakeLists.txt 树**：按 `add_subdirectory()` 顺序递归读入——
   - `firmware/`（CubeMX 生成的 HAL、启动文件，定义了可执行目标 `firmware`
     和接口库 `stm32cubemx`）
   - `drivers/tmc5240/` → 静态库 `tmc5240`
   - `application/` → 静态库 `app`
   - 顶层 `CMakeLists.txt` 第 49 行 `target_link_libraries(firmware app)`
     把业务逻辑挂进最终固件
3. **修链接脚本路径**：顶层 `CMakeLists.txt` 第 24-27 行把 CubeMX 写死的
   `STM32H743xx_FLASH.ld` 路径替换为 `firmware/` 下的真实位置。
4. **生成产物**（都在 `build/Debug/` 里）：
   - `CMakeCache.txt` — 配置结果缓存
   - `build.ninja` — **核心产物**：一份包含每个源文件怎么编译、什么顺序的
     "说明书"（即 DAG 依赖图）
   - `compile_commands.json` — 每个文件的完整编译命令，
     **给 clangd 做代码补全/跳转用，不参与实际编译**。这就是 clang 在本工程里唯一的角色。
   - `CMakeFiles/rules.ninja` — 各类规则模板

## 2. 构建阶段（Ninja 的工作）

Ninja 拿到 `build.ninja` 后：

1. **构建依赖图**：`firmware.elf` ← 所有 `.obj` ← 各源文件；
   库依赖顺序为 `app`、`tmc5240`、`STM32_Drivers` 先编，最后链接可执行文件。
2. **增量判断**：对比每个 `.c` 文件和它对应的 `.obj` 的时间戳
   （以及 `.obj.d` 里记录的头文件依赖）。只重编改过的文件——
   这就是点两次编译，第二次瞬间完成的原因。
3. **并行调度**：默认按 CPU 核数并行发起多条 gcc 命令。
4. 如果发现 `CMakeLists.txt` 被改过，会自动重新执行一次配置阶段
   （`cmake --regenerate-during-build`，见 `rules.ninja` 第 103 行）。

## 3. 单个文件的编译（GCC 的四步）

以 `main.c` 为例，`build.ninja` 第 81-89 行声明了它。实际展开的命令是
（编译器是 GCC 的驱动器，内部依次调用 cpp → cc1 → as）：

```
arm-none-eabi-gcc
  -DDEBUG -DSTM32H743xx -DUSE_HAL_DRIVER -DUSE_PWR_LDO_SUPPLY   ← 宏定义
  -I.../Core/Inc -I.../HAL_Driver/Inc ...                       ← 头文件搜索路径
  -mcpu=cortex-m7 -mfpu=fpv5-d16 -mfloat-abi=hard               ← 目标芯片
  -Wall -fdata-sections -ffunction-sections -fstack-usage       ← 工具链文件第 29 行
  -O0 -g3 -std=gnu11                                            ← Debug 配置
  -MD -MT xxx.obj -MF xxx.obj.d                                 ← 生成依赖文件
  -o firmware/CMakeFiles/firmware.dir/Core/Src/main.c.obj -c
     firmware/Core/Src/main.c
```

内部流程：

- **预处理**：展开 `#include`（HAL 头文件）、宏替换，得到单个巨型 `.i` 文件
- **编译**：C → Cortex-M7 汇编
- **汇编**：生成 ARM 机器码目标文件 `.obj`
- 副产物：
  - `.obj.d`（头文件依赖，供下次增量判断）
  - `.su`（`-fstack-usage` 生成的栈用量统计，`build/Debug` 里那 33 个 `.su` 文件就是它）

## 4. 打包静态库（ar + ranlib）

`app`、`tmc5240`、`STM32_Drivers` 是静态库，编完 `.obj` 后 Ninja 执行
（`rules.ninja` 第 75 行）：

```
arm-none-eabi-ar qc libapp.a  app.c.obj tmc5240_port.c.obj   ← 把 .obj 收进库
arm-none-eabi-ranlib libapp.a                                ← 建立符号索引
```

## 5. 最终链接（生成 .elf）

所有依赖就绪后（`build.ninja` 第 169 行），Ninja 执行链接命令。
链接器仍是 gcc/g++（它只是替你调用了内部的 `ld`）：

```
arm-none-eabi-gcc  <所有 .obj> -o firmware/firmware.elf
  -mcpu=cortex-m7 ...
  -T firmware/STM32H743xx_FLASH.ld      ← 内存布局：FLASH/ITCM/DTCM/RAM 怎么分
  --specs=nano.specs                    ← 用精简版 newlib（省 Flash）
  -Wl,-Map=stm32h742zit6_tmc5240.map    ← 生成 map 文件（符号/段地址表）
  -Wl,--gc-sections                     ← 裁掉没被引用的段（配合前面的
                                           -ffunction-sections 才有效）
  -Wl,--print-memory-usage              ← 链接完打印 RAM/FLASH 占用百分比
  -lm                                   ← 链接数学库
```

链接器做的工作：把启动文件 `startup_stm32h743xx.s` 的向量表、各 `.obj` 的代码段
数据段，按 `.ld` 脚本规定的地址搬运进绝对地址空间，解析所有跨文件的函数/变量引用，
最后输出 **`firmware.elf`**（含调试信息，可直接被 OpenOCD/ST-Link 烧录或 GDB 调试）。

## 6. 各工具角色一览

| 工具 | 在本工程的角色 |
|---|---|
| **CMake** | 构建系统生成器：把 CMakeLists.txt 翻译成 build.ninja，之后只在配置变化时重新出场 |
| **Ninja** | 实际的构建执行器：按依赖图、增量、并行地发起编译命令（本工程**没有 Makefile**） |
| **GCC (arm-none-eabi-)** | 真正干活的交叉编译器：预处理/编译/汇编/链接一体 |
| **clang / clangd** | **不编译任何东西**。只消费 `compile_commands.json` 做 IDE 的代码分析 |
| **ar / ranlib / objcopy** | binutils 工具：打包静态库 / 生成 `.bin`/`.hex`（如需） |

## 7. 一句话总结

**点编译 → CMake 确认 build.ninja 是最新的 → Ninja 依图调度 →
arm-none-eabi-gcc 逐文件编译、ar 打库、gcc 链接 → 产出
`build/Debug/firmware/firmware.elf`**，之后 IDE 再通过烧录工具把这个 elf 写进芯片。

# 附：搭建这套开发环境需要安装的软件

## 8. 必装软件清单

| 软件 | 版本要求 | 作用 | 官方下载地址 |
|---|---|---|---|
| **Arm GNU Toolchain (arm-none-eabi)** | 13.3.Rel1（本工程实际使用） | 交叉编译器 gcc/g++/ar/ranlib/objcopy | developer.arm.com → "GNU Toolchain" → 选 `arm-none-eabi` Windows 版 (mingw-w64-i386 安装包) |
| **CMake** | ≥ 3.22（工程要求），建议 3.28+ / 4.x | 构建系统生成器 | cmake.org/download → Windows x64 Installer（安装时勾选 *Add CMake to the system PATH*） |
| **Ninja** | ≥ 1.5 | 实际执行编译的工具 | 任选其一：① 下载 [w64devkit](https://github.com/skeeto/w64devkit/releases)（自带 ninja，本工程即用此方式）；② `pip install ninja`；③ 从 ninja-build.org 下载 `ninja-win.zip` |
| **VS Code** | 最新版 | 编辑器 / IDE 入口 | code.visualstudio.com |
| **ST-Link 驱动 + 烧录工具** | — | 烧录 elf/bin 到芯片、调试 | ST 官网：STSW-LINK007（驱动）、STM32CubeProgrammer（烧录）、OpenOCD（调试服务器，xpack 或 STM32CubeIDE 自带均可） |

> 说明：**不需要安装 Make**（Ninja 取代了它），**不需要装 clang**（clangd 插件会自带或单独指定，仅用于代码分析）。

|---|---|---|---|

| clangd | `llvm-vs-code-extensions.vscode-clangd` | 基于 `build/Debug/compile_commands.json` 的更快的代码补全/跳转（与 cpptools 二选一，二选一时需在设置中禁用 cpptools 的 IntelliSense） | ⭕ 可选 |
| Serial Monitor | `ms-vscode.vscode-serial-monitor` | 串口监视器，看 printf 日志（本工程 shell/日志组件用得上） | ⭕ 可选 |

CMake Tools 无需手动写 `cmake-tools-kits.json`：它读取根目录的 `CMakePresets.json`，
在状态栏选择 **Debug** 或 **Release** 预设后，点 Build（或按 `F7`）即等价于
`cmake --build build/Debug`。

## 10. PATH 环境变量设置（Windows）

把以下三个目录加入系统 `Path`（`此电脑 → 属性 → 高级系统设置 → 环境变量 →
系统变量 → Path → 编辑 → 新建`）：

```text
C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\13.3 rel1\bin
C:\Program Files\CMake\bin
<w64devkit 解压目录>\bin          ← 提供 ninja.exe（或用 pip/独立下载的 ninja 目录）
```

可选（用到烧录/调试时再加）：

```text
C:\Program Files\STMicroelectronics\STM32Cube\STM32CubeProgrammer\bin   ← STM32_Programmer_CLI.exe
<OpenOCD 安装目录>\bin                                                  ← openocd.exe
```

### 验证安装

重新打开一个 PowerShell / CMD 窗口（改 PATH 后必须重开终端才生效），逐条执行：

```powershell
arm-none-eabi-gcc --version    # 应输出 13.3.x，target: arm-none-eabi
cmake --version                # 应 ≥ 3.22
ninja --version                # 应 ≥ 1.5
```

三条都有正常输出，即可在 VS Code 中打开本工程，
CMake Tools 会自动按预设完成配置并开始编译。

### 常见问题排查

| 现象 | 原因 | 解决 |
|---|---|---|
| `CMake Error: No CMAKE_C_COMPILER could be found` | `arm-none-eabi-gcc` 不在 PATH | 检查第 10 节第一条路径；重开终端 |
| `ninja: command not found` / CMake 报找不到生成器 | Ninja 未安装或不在 PATH | 安装后重开终端 |
| 编译能过但 clangd 报一堆红波浪线 | clangd 找不到编译数据库 | 先成功配置一次生成 `build/Debug/compile_commands.json`，并在 `.vscode/settings.json` 中无需额外配置（clangd 默认会查找该文件） |
| 首次配置卡在检测编译器 | 工具链文件需要 `arm-none-eabi-` 前缀工具在 PATH | 见上 |
| 链接报错找不到 `STM32H743xx_FLASH.ld` | 工具链文件用了旧路径 | 本工程顶层 CMakeLists.txt 已自动替换为 `firmware/` 下的路径，无需处理 |
